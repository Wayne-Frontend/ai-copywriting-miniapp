# AI 文案工具微信小程序——项目概述（Project Overview）

**文档版本：** V1.0  
**项目状态：** 待开发 / MVP 阶段  
**项目类型：** 微信小程序 + 后端 API + Web 管理后台  
**产品名称：** 文案轻工坊（暂定，正式上线前需进行名称及商标核验）  
**目标平台：** 中国大陆微信小程序  
**核心原则：** 场景固定、操作简单、成本可控、安全合规、稳定可靠、可持续商业化。

---

## 一、项目名称与定位

### 1.1 项目名称

**文案轻工坊——AI 智能文案生成助手**

英文项目代号：`ai-copywriting-miniapp`

### 1.2 一句话简介

一款面向自媒体创作者、职场人士和学生的微信 AI 文案工具，通过选择固定场景、填写少量关键信息，即可快速生成、优化和管理实用文本内容。

### 1.3 产品定位

本项目定位为 **固定场景 AI 文案生成工具**，而非通用 AI 聊天机器人。

产品采用“选择模板 → 填写信息 → AI 生成 → 编辑复制”的标准化工作流，降低普通用户使用大模型的门槛。

核心价值：

- **简单：** 不需要用户学习 Prompt，使用表单即可生成文案。
- **高效：** 将复杂写作过程简化为少量输入和一次生成。
- **实用：** 聚焦日常高频写作任务，生成可直接编辑使用的文本。
- **可控：** 通过固定模板、字数限制、额度控制降低 API 成本。
- **可信：** 对 AI 生成内容、使用限制及高风险场景进行明确提示。

### 1.4 核心用户路径

打开小程序 → 选择文案模板 → 填写必要信息 → 点击生成 → 查看结果 → 复制、保存或改写。

首次使用不强制填写手机号；在需要建立用户身份、保存历史或购买服务时，通过微信登录机制完成身份识别。

## 二、目标用户与角色权限

### 2.1 普通用户（主要服务对象）

| 用户类型 | 典型需求 | 产品价值 |
|---|---|---|
| 自媒体创作者 | 小红书标题、内容脚本、短视频口播、朋友圈文案 | 提高内容创作效率 |
| 职场人士 | 周报、会议纪要、工作邮件 | 减少重复性写作 |
| 学生群体 | 作文提纲、论文大纲、写作思路 | 辅助构思与学习，不代写学术成果 |

普通用户分为免费用户和付费用户，两者使用相同的基础生成流程，主要区别在于可使用额度。

普通用户权限包括：浏览模板、生成文案、复制内容、保存与删除历史、查看剩余额度、购买套餐、查看订单、管理个人数据。

### 2.2 管理员（平台运营人员）

管理员通过独立 Web 管理后台操作，不直接使用小程序前端管理业务。

管理员权限包括：

- 查看用户数量、生成次数、付费订单和 API 消耗。
- 管理模板的启用状态、表单配置、Prompt 版本。
- 管理套餐价格、额度及展示状态。
- 查询订单、处理异常订单和退款。
- 查看生成失败、内容审核和系统告警记录。
- 配置限流、模型路由和风险控制策略。

后台采用基于角色的权限控制，初期仅设置超级管理员和运营管理员两类角色。

### 2.3 企业客户（非 V1.0 目标）

未来可考虑面向企业提供团队额度、统一结算和企业文案模板。

**V1.0 不开发企业版、不支持企业组织、多租户、团队协作、企业专属模型或开放 API。**

## 三、核心业务目标

### 3.1 用户价值目标

解决三个主要问题：

1. **不知道怎么写：** 用户不需要自行编写复杂提示词，通过模板和字段引导即可完成创作。
2. **写作耗时长：** 对常见的重复性文本提供快速生成与改写能力。
3. **通用 AI 操作复杂：** 避免开放式聊天交互，让用户始终围绕具体任务操作。

### 3.2 商业目标

建立“免费体验 → 高频使用 → 额度消耗 → 付费购买 → 持续复购”的商业闭环。

V1.0 采用免费额度、次数包和月度额度包三种方式。

| 套餐 | 初步配置 | 说明 |
|---|---|---|
| 免费版 | 每日 5 次 | 每日北京时间 00:00 重置，不累计 |
| 次数包 | ¥9.9 / 50 次 | 按成功生成次数扣减 |
| 月度包 | ¥19.9 / 300 次 | 购买后 30 天内有效，不自动续费 |

**定价决策说明：** 原始方案中的“19.9 元包月无限次”暂不纳入 V1.0。无限调用存在成本不可控及自动化滥用风险，建议先采用明确额度的月度包。300 次为待验证参数，应根据真实模型成本、用户使用量和毛利情况调整。不得将有限额度套餐宣传为“无限次”。

计费原则：

- 只有生成成功才最终扣减额度。
- 失败或系统超时且未交付有效结果时，不扣费或自动返还预占额度。
- 重新生成和再次改写属于新的生成请求，按规则消耗额度。
- 防止重复请求、重复支付回调和重复扣费。
- 用户可查看额度来源、有效期和使用记录。
- 套餐有效期、退款规则在购买前明确展示。

### 3.3 首期业务验证指标

以下均为试运营目标，不代表已有数据：

- 新用户首次生成完成率 ≥ 80%。
- AI 生成任务成功率 ≥ 98%（按约定统计口径）。
- 生成结果复制或保存率 ≥ 40%。
- 用户反馈有用率 ≥ 80%。
- 建立付费转化率、单次生成成本、付费用户毛利和次月复购率监控。

## 四、项目范围与功能边界

### 4.1 V1.0 必须实现的功能（P0）

**A. 文案生成模块**

首期只上线 10 个固定场景：

| 分类 | 功能 | 核心输入 |
|---|---|---|
| 自媒体 | 小红书标题生成 | 主题、受众、风格 |
| 自媒体 | 小红书内容脚本 | 主题、卖点、语气 |
| 自媒体 | 短视频口播稿 | 主题、时长、风格 |
| 自媒体 | 朋友圈文案 | 主题、场景、语气 |
| 自媒体 | 文案润色改写 | 原文、改写目标 |
| 职场 | 工作周报 | 工作事项、成果、计划 |
| 职场 | 会议纪要 | 用户提供的会议记录、待办事项 |
| 职场 | 工作邮件 | 收件对象、目的、要点 |
| 学生 | 作文提纲 | 题目、年级、写作方向 |
| 学生 | 论文大纲 | 研究主题、方向、结构要求 |

统一采用配置驱动的模板引擎，不为每一个场景单独开发完整业务系统。

学生场景仅提供思路、提纲和结构建议，不生成可直接提交的完整论文，不编造参考文献、研究数据或实验结果。

**B. 文案生成与结果处理**

- 动态表单输入与必填字段校验。
- 字数、语气、风格等有限选项。
- 生成状态展示：排队中、生成中、成功、失败。
- 生成结果展示、复制、保存、删除。
- 再次生成、基于现有内容改写。
- 内容风险审核及失败提示。
- 生成结果明确标识为 AI 生成内容。

首期每次请求只生成一份主要结果；单次输入和输出长度按模板配置上限，禁止无限长度生成。

**C. 用户与账户**

- 微信身份登录。
- 用户基础资料及账户状态。
- 免费额度与付费额度管理。
- 历史记录查询、保存、删除。
- 用户协议、隐私政策、个人信息删除入口。

**D. 支付与订单**

- 微信支付接入。
- 次数包和月度包购买。
- 订单创建、支付回调验证、订单查询。
- 支付成功后额度发放。
- 支付异常处理、退款及对账。
- 额度流水和订单幂等控制。

**E. 运营管理后台**

- 管理员登录与权限校验。
- 用户、订单、额度查询。
- 模板与 Prompt 版本管理。
- 套餐管理。
- 生成统计、API 成本统计。
- 审核记录、错误日志和系统告警。

### 4.2 V1.1 候选功能（P1，暂不开发）

首期上线并验证核心数据后，再决定是否增加：

- 公众号短文案生成。
- 标题优化。
- 月报生成。
- 简历润色。
- 述职报告。
- 面试自我介绍。
- 读后感思路与读书笔记。
- 风险词提示及基础规则检测。

风险词检测只能定位为辅助提示，不得承诺能够识别所有违规内容或保证通过第三方平台审核。

合同简易草稿暂不开发；未来如需纳入，必须先进行法律风险和平台规则评估，并提供醒目的“仅供参考，不构成法律意见”提示。

### 4.3 明确不做的功能（Out of Scope）

V1.0 严格排除以下能力：

- 通用 AI 聊天、多轮自由对话、AI 智能体。
- AI 图片、视频、语音生成。
- 录音转写、音视频上传、文件解析。
- 联网搜索、实时热点抓取、第三方平台自动发布。
- 直接生成完整学术论文或伪造学术材料。
- 合同法律效力审查、专业法律咨询。
- 企业协作、多租户、开放 API。
- 自动续费订阅。
- 积分签到、邀请裂变、广告变现。
- 自训练大模型、模型微调、向量知识库、RAG。
- 复杂推荐算法、社区、社交功能。

**范围控制规则：任何未列入 P0 的功能，不允许 AI 编程工具自行添加。新增需求必须先修改项目需求文档，并明确优先级、成本和验收标准。**

## 五、技术栈初步选型

### 5.1 技术选型总表

| 层级 | 技术选型 | 用途 |
|---|---|---|
| 小程序前端 | 微信原生小程序 + TypeScript | 用户端 |
| UI 组件 | TDesign Miniprogram | 表单、弹窗、列表等 |
| 管理后台 | Vue 3 + TypeScript + Vite + Element Plus | 运营管理 |
| 后端 | Node.js 24 LTS + NestJS 11 + Fastify | API 与业务服务 |
| 数据库 | PostgreSQL 18.4 | 用户、订单、额度、历史记录 |
| ORM | Prisma | 数据访问和迁移 |
| 缓存与限流 | Redis 7 | 限流、短期缓存 |
| 异步任务 | BullMQ | AI 生成任务队列 |
| AI 接入 | 服务端大模型适配层 | 调用合规可用的文本模型 API |
| 支付 | 微信支付 API v3 | 小程序支付及回调 |
| 部署 | Docker + 腾讯云托管容器服务 | 应用运行与扩容 |
| 数据服务 | 腾讯云托管 PostgreSQL、Redis | 高可用数据存储 |
| 监控 | 结构化日志 + 指标监控 + 告警 | 故障发现和定位 |
| 工程管理 | Git + pnpm Workspace + CI/CD | 代码、测试、发布 |

依赖具体版本和兼容性在项目初始化时统一锁定，禁止在开发过程中未经评审随意更换框架。

### 5.2 架构原则

整体采用**模块化单体后端 + 独立 AI 异步任务 Worker**。

核心流程：

小程序 → NestJS API → 参数校验与内容审核 → 额度预占 → Redis 任务队列 → AI Worker → 模型服务 → 输出审核 → 数据库持久化 → 返回结果并确认扣费。

AI 模型只能通过后端调用，API Key 不得存放在小程序代码中。

AI 模型采用适配器接口，首期确定一个主模型供应商，并预留备用供应商切换能力。模型选择以中国大陆合规适用性、文本效果、成本、延迟和稳定性为依据。

### 5.3 后端模块划分

后端按以下业务模块组织：

- `auth`：微信登录、会话、管理员鉴权。
- `users`：用户资料与账户状态。
- `templates`：场景模板与 Prompt 配置。
- `generations`：生成任务、结果与历史记录。
- `ai`：模型调用、超时、重试、路由。
- `credits`：额度、预占、扣减、返还和流水。
- `payments`：支付订单、回调、退款、对账。
- `moderation`：输入输出审核与风险控制。
- `admin`：管理接口与审计日志。
- `observability`：日志、监控、告警。

首期核心数据表包括：

`users`、`templates`、`generation_jobs`、`saved_contents`、`credit_accounts`、`credit_ledger`、`orders`、`entitlements`、`admin_audit_logs`。

数据库结构应支持未来新增模板和套餐，但不提前实现企业多租户等非本期能力。

### 5.4 高可用与可靠性要求

本项目虽为轻量文本工具，但支付和额度系统必须达到生产环境可靠性要求。

**服务可用性**

- 生产环境 API 服务至少部署 2 个实例。
- 数据库采用托管高可用配置，并启用自动备份。
- Redis 使用托管高可用配置。
- AI 任务支持排队、状态查询、超时和有限重试。
- 主模型异常时支持降级提示或切换备用模型。
- 模板配置变更支持版本管理和回滚。

**数据一致性**

- 支付回调必须验签、幂等处理。
- 额度变更必须记录不可随意覆盖的流水。
- 并发生成不得导致额度超扣。
- 失败任务必须释放预占额度。
- 同一请求使用幂等标识，避免网络重试重复扣费。

**安全与隐私**

- 服务端鉴权、参数校验、接口限流。
- 管理员操作审计与最小权限。
- API 密钥使用服务端密钥管理。
- 日志脱敏，不记录不必要的完整用户输入。
- 用户内容按明确的数据保留规则处理，支持删除。
- 对生成内容进行输入输出风险审核。

**初始非功能目标**

- 自有 API 服务月可用性目标：99.9%。
- 普通业务接口 P95 响应时间目标：500ms 内（不包含外部服务耗时）。
- AI 任务 P95 完成时间目标：20 秒内，具体以模型压测结果校准。
- 生成任务成功率目标：98% 以上。
- 订单与额度操作不得发生已知的重复入账、重复扣费问题。

上述为设计和验收目标，不是未经验证的服务承诺；微信平台和外部模型故障应单独监控。

### 5.5 技术开发约束

1. 前后端统一使用 TypeScript。
2. 后端使用 REST API，不引入 GraphQL。
3. 不采用微服务、Kubernetes 或复杂分布式架构。
4. Prompt 模板配置化、版本化，不直接散落在业务代码中。
5. 支付、额度、订单操作必须具备自动化测试。
6. 每个业务模块必须有明确的输入输出和错误处理。
7. 开发、测试、生产环境隔离。
8. 任何第三方服务调用都必须设置超时及失败处理。
9. 所有新增依赖必须说明用途，避免无意义的技术复杂度。

### 8.2 MVP 验收条件

只有同时满足以下条件，才视为 V1.0 开发完成：

- 10 个模板均能完成输入、生成和结果操作。
- 免费额度、次数包和月度包正确计费。
- 支付、订单、额度数据保持一致。
- 生成失败、支付异常、网络重试均有明确处理。

## 九、项目最终开发原则

**产品原则：** 只解决固定场景下的文本生成与优化问题，不发展为通用 AI 平台。

**交互原则：** 模板优先、输入简洁、结果明确，避免复杂配置。

**技术原则：** 优先成熟技术、模块化单体、托管基础设施，不进行超前架构设计。

**商业原则：** 先验证真实需求、付费意愿和单位成本，再决定是否扩展套餐和模板。

**安全原则：** 支付一致性、用户数据保护、内容审核和模型调用安全属于上线必需能力。

**范围原则：** V1.0 仅实现本文件明确列出的 P0 功能。P1 和 Out of Scope 不得自动进入开发任务。

**最终交付目标：** 一个能够在微信小程序内完成真实 AI 文案生成、额度计费、微信支付、历史管理及后台运营的可上线 MVP，而不是只有演示页面的原型项目。
